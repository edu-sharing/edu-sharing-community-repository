# edu-sharing Frontend-Server

Delivers the edu-sharing Angular app (`Frontend-Server/`, Node/Fastify) and proxies the
backend paths it receives to the repository service. Stateless - a `Deployment`,
scalable via `replicaCount` / `autoscaling`.

## Routing: split between this chart and the repository service chart

Both charts publish Ingresses for the **same hosts** (`ingress.hosts`); nginx picks the
longest matching path:

| Path | Chart | Service port |
|------|-------|--------------|
| `/` (exact) | this chart - the frontend server redirects to the context path | `service.port.api` |
| `/edu-sharing` (prefix, catch-all) | this chart | `service.port.api` |
| `/edu-sharing/rest`, `/eduservlet`, `/login`, `/logout`, `/preview`, `/webdav` | repository service chart (`ingress.paths`) | its `service.port.api.external` |

Every other backend path (`/shibboleth`, `/saml2`, `/oauth2`, `/sso`, ...)
reaches Tomcat through the frontend server, which proxies it
(`Frontend-Server/src/routes/backend-paths.ts`). Sessions are shared via redis, so it
does not matter which repository pod such a request lands on.

## Ports of the repository service

The frontend server talks to the repository service directly, not via the ingress:

* `config.backend.port.external` - everything proxied and the node metadata fetched on
  behalf of the browser. Must be the service chart's `service.port.api.external` (the
  proxy sidecar or the external connector): Tomcat skips 2FA on its internal port.
* `config.backend.port.internal` - the config fetches only (`ValuesBackendInternal`),
  the service chart's `service.port.api.internal`.

## Probes and metrics

On the management port (`service.port.management`): `GET /health/liveness` (never asks
the backend), `GET /health/readiness` (ready once the backend was reached) and
`GET /metrics` (prometheus, `ServiceMonitor` with `global.metrics.servicemonitor.enabled`).
Never exposed through the ingress.

## Istio

Not supported yet: the path split needs a single `VirtualService` for both charts, since
Istio does not order routes across `VirtualService`s of the same host. With
`global.cluster.istio.enabled` the chart refuses to render.

## Resources and scaling

Node handles all requests on **one thread** (the event loop); only the libuv threadpool
(static file reads, zlib) and the garbage collector run on further threads. Hence:

* **`resources.limits.cpu`: 1 CPU is the sensible maximum.** More is hardly used; scale out
  with `replicaCount` / `autoscaling` (CPU based HPA) instead of up.
* Repeat visits are cheap: the hashed bundles are served `immutable`, so the browser only
  fetches the shell and the REST calls again.
* One process per pod - no `node:cluster`: every worker would bring its own metrics
  registry, config cache, `_about` poll and memory.

**Memory:** the image sets `NODE_OPTIONS=--max-old-space-size-percentage=40`, so the V8 heap
follows `resources.limits.memory` (the cgroup limit): 105 MB at 256Mi, 207 MB at 512Mi,
457 MB at 1Gi. Without it node would take at least ~259 MB - more than a 256Mi container.
Measured: the app itself uses 25-45 MB heap even at hundreds of requests per second, but the
resident memory grows to ~300 MB under heavy load (young generation, socket buffers,
streams). The default `256Mi` fits normal operation; for high load (hundreds of concurrent
connections per pod) raise `resources.limits.memory` to `512Mi` - a limit is not reserved,
only `requests` is. Override the percentage via `config.extraEnv.NODE_OPTIONS`.

**Static file cache:** every file up to `config.staticCache.maxFileMb` (8 MB) is read once per
pod and served from memory, text formats as gzip / brotli. `config.staticCache.maxMb: auto`
takes 20 % of the container memory limit (16-256 MB) - the buffers live outside the V8 heap,
so they count against `resources.limits.memory`, not against the heap. At 256Mi that is
51 MB; the first page needs ~10 MB, the three largest bundles ~10 MB each when requested.
Heap (40 %) + cache (20 %) leave ~40 % to code, sockets and streams.

## Debugging in the cluster

`debug: true` (or `global.debug: true` for all charts) switches the pod to DEV mode (dev
response headers `X-Proxy-Reason` / `X-Proxy-Upstream` / `X-Proxy-Time`, request logging)
and starts node with the inspector on the pod's loopback (`127.0.0.1:9229`) - the same
idea as the JDWP port 5005 of the repository service chart. It is never published through
a Service or the ingress; attach through a port-forward:

```bash
kubectl -n <namespace> port-forward deploy/edusharing-repository-frontend-server 9229:9229
```

then Chrome `chrome://inspect` (configure `localhost:9229`) or VS Code
(`"request": "attach", "port": 9229`, `"localRoot": "${workspaceFolder}/Frontend-Server/build"`,
`"remoteRoot": "/app/build"`). With several replicas `deploy/...` picks one pod - use
`pod/<name>` to choose. The inspector can run arbitrary code in the process: debugging
clusters only.
